# Questions for the specification

Points where the examples or the spec chapter (`presk-specs`,
`report/chapters/02-spec.tex`, `presk-draft-spec.md`) leave the compiler a
choice. Each entry records the provisional answer implemented in 0.1.0; the
answer is to be settled in the spec, after which this file is updated.

| # | Question | Provisional answer in 0.1.0 | Status |

| 2 | No EBNF for `optimizer`, `training run`, `inference serve`, `model`, `import`, `type`, `static assert`, `dim … <=` | schema table in `presk-types::check::config` | open |

| 29 | What `batch(B)` does to samples, and where the language-modelling shift between inputs and targets happens | `batch(B = n)` stacks `n` samples under a `batch` axis and binds the objective's `B`; `shuffle(seed)` is re-keyed per epoch; `take(n)` keeps the first `n` batches; the shift is data preparation (`presk data lm-windows`), not a semantics of `stream` | open |
| 30 | The optimizer is "a pure function (θ, state, grad) → (θ', state')" with no state type, update rule or schedule formula | AdamW as PyTorch defines it (decoupled weight decay, bias-corrected moments, `eps` added to the square root, global-norm clipping first), state = the two moments, `t` from the loop; `constant`, `linear(warmup)`, `cosine(warmup)` over `epochs × batches` steps decaying to 0; defaults `betas = (0.9, 0.999)`, `eps = 1e-8`; clipping uses `c / (‖g‖ + 1e-6)` as PyTorch; the block's *name* is the algorithm (`optimizer adamw`), `adamw` only in 0.2.0 (D17) | open |

| 44 | Are two tensors that differ only in their axis *names* the same value? The checker types `ŷ − y` as `ℝ[batch: B, model: D]` when `ŷ : ℝ[batch: B, D]` (names are filled in by the other operand), and the interpreter's `sum_to x t` returns `x`'s data under `t`'s names; a rewrite `sum_to x t → x` that is exact over ℝ can therefore change the names a downstream `softmax(axis …)` sees | `presk-opt` applies the identity only when the two static types agree *including names*; the spec could state that a value is a tensor with named axes (names part of the denotation), or that names are static annotations erased at run time (then the interpreter should not carry them and `axis` arguments should resolve statically) | open |
| 45 | The language can split and merge *attention* axes (`split_heads`/`merge_heads`, tied to `const H`/`HD`) but has no general way to merge two adjacent axes, which the embedding MLP needs (`ℝ[batch, ctx: C, emb: E] → ℝ[batch, model: C·E]`) | `merge(axis a, axis b, x)` (0.4.0 step 1): the two axes must already be adjacent and in that order, since joining distant axes would also transpose and `merge` moves no data; the merged length is their product, so at least one must be constant (`E1007` otherwise); the joined axis is **unnamed**, because neither input name describes it and `a_b` would be arbitrary — the context names it, as it names `embed`'s and `one_hot`'s. A surface `split` is not needed by the corpus and stays internal (`reshape_like`, the adjoint). **Finding: `split_heads`/`merge_heads` are not sugar for a general split/merge**, because they also permute (`ℝ[batch, seq, model] → ℝ[batch, heads, seq, hd]` moves `heads` before `seq`); the attention pair stays primitive until the language has a transpose, which the specification should decide. Related: `embed` now carries the name of its table's second axis into the result, so the new axis can be referred to at all | open |
| 46 | `embed` is described as "one-hot × table" but `one_hot` is not in the standard library, so the counting bigram cannot be written | `one_hot(ids) -> ℝ[..., V]` (0.4.0 step 1), `Disc` in its argument; `embed` keeps its own primitive for the gather | open |
| 47 | Tokenization: is the vocabulary part of the program (a `const V` plus a table) or of data preparation? | data preparation (`presk data chars\|bpe`); the program sees only `V`. The specification may want a `tokenizer` declaration so that a served model carries its vocabulary | open |
| 48 | Per-step keys for `dropout` (question 33, open since 0.2.0) | **answered in 0.4.0 step 3 by putting the key in the signature**: `dropout(rate, key, x)` draws its mask from the key alone and `split_key(key) -> (key, key)` gives independent ones. This is a correctness requirement, not a style: differentiation recomputes the forward pass, so a mask from a hidden stream would differ between forward and backward and the gradient would be silently wrong; a mask that is a function of the key recomputes identically, and `dropout` needs no adjoint rule of its own. An objective may take a per-step key between `θ` and the batch, which the loop derives from the run's seed. Outside a training run the mask is all ones — the expectation of the random function — so `run`, `serve` and the export evaluate the model's mean, and the export emits `F.dropout(x, p, training=False)` since a Presk key cannot drive PyTorch's generator. **What is left**: a `stack{L}` fold passes the same extra arguments to every iteration, so the blocks of a stacked module share one key; independent per-layer keys need a key derived from the loop index, which the specification should settle (a `split_key(key, i)`, or the fold passing its index to the body) | open |
| 49 | With fusion, `Q` is per group and extraction is a joint choice of term and partition (cost-model document §1.2 proposes ILP or dynamic programming) | **partly done in 0.4.0 step 4**: the partition exists (`presk-sched`, greedy, structural, computed after extraction) and is measured — on the optimizer's chain it removes 73 % of the launches and 15 % of the time, a traffic effect the roofline's `Q` predicts in shape. The extraction still costs each node on its own, so it under-counts what fusion will save; making the two one decision, by ILP or by dynamic programming over the e-graph, is the open part. The specification should also say whether a group's cost belongs to PSK-Core's `T̂` or to PSK-Sched's, given that the partition is chosen after the term | open |
